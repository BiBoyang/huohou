# polish（写作润色）

让文字读起来像"一个清楚自己在说什么的人写的"，而不是机器糊的或翻译过来的。

## 先问清楚（一次问完）

- 发在哪：公众号 / 技术博客 / 文档 / 邮件——语气和格式要求不同
- 读者是谁：同行、小白、客户
- 有没有必须保留的东西：术语、特定措辞、个人口头禅

## 润色优先级（按此顺序动刀，不平均用力）

1. **事实与术语**——先修错的：事实错误、术语误用、逻辑矛盾。顺手核查事实性断言，存疑的标出来问作者，不擅自改
2. **前提与信息缺失**——版本、环境、上下文有没有交代；缺了提醒作者补，不替他编造
3. **逻辑链**——现象→原因→方案→验证有没有断层；一段只承担一个功能，塞多了就拆
4. **废话与套话**——空洞过渡、正确的废话、模板化总结；去掉后信息量零损失的全删
5. **代码与示例**——代码不当装饰物：裁掉陪衬部分，关键行要有解释
6. **边界与代价**——"更快/更安全/推荐"这类说法，补上适用条件、代价、不适用场景
7. **去翻译腔**（中文重点）——长定语从句拆开、被动转主动、抽象名词转动词（"进行优化"→"优化"）、英文连接词直译换成中文行文节奏
8. **语气与 AI 味**——最后才处理：打散过于工整的句式、删"首先其次最后"骨架痕迹、保留作者自己的腔调

先判断这篇最主要的问题属于哪一类（事实 / 结构 / 信息缺失 / 废话 / 语气模板化），优先改最影响可读性的部分。

## 专项参考

- 技术文章（教程、踩坑、原理、方案对比）：读 `references/tech-article.md`，有专项清单和 12 问自检
- AI 味拿不准、需要具体禁用词表：查 `references/anti-ai-flavor.md`

## 红线

- **不改原意**——拿不准作者的意图就标注提问，不替他做决定
- **不抹掉个人风格**——口语化、毒舌、碎碎念都是风格，只修歧义和啰嗦，不统一成"标准文体"
- **不注水**——润色后的字数只许少于等于原文，除非作者要求扩写
- **不编造**——不替作者编经历、测试数据、引用来源；信息不够就标"这里需要作者补充"
- 改动大的地方，给一句"为什么这样改"

## 输出方式

- 短文（<500字）：直接给改后全文 + 关键改动说明
- 长文：分段处理，每段给"原文 → 改后 → 理由"，作者确认后再下一段
- 末尾附一句整体诊断：这段文字最大的问题是什么（一句话）
