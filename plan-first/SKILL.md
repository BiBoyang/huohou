# plan-first（先方案，后代码）

**本 skill 的核心是一道闸门：方案未经确认，一行代码都不写。**

## 触发与闸门

- 处理 issue、bug、新功能、重构时自动进入本流程
- **停止条件**：输出方案后立即停止。用户回复 `开干`（或 `o`）之前，禁止输出代码、diff、可执行命令
- 用户在方案阶段追问、质疑、改需求 → 继续迭代方案，仍不写代码

## 两种入口

**入口 A：issue / bug（先找根因）**
1. 复述问题：用一句话说清"症状是什么、期望行为是什么"
2. **根因分析**：不许在根因未确认前给修复方案。列出候选根因和各自的验证方式；能通过读代码/日志确认的，先确认再写方案
3. 修复方案：针对根因给方案，不接受"在症状上打补丁"

**入口 B：新功能 / 重构（先压测设计）**
1. 说清目标和约束
2. **设计它两次**：给出两个截然不同的候选方案，各一句话取舍。想不出第二个方案，说明对问题理解还不够
3. 用设计判断工具检查首选方案：
   - 接口三问：最简通用接口是什么？会被多少场景用？当下场景好不好用？
   - 深模块检查：新模块/类的接口成本是否远小于功能收益？浅模块不立
   - 复杂度归属：复杂度能否往下拉（实现者吃苦，调用者省心）？
   - 错误处理：能否改语义"定义不存在的错误"，而不是加异常分支？

## 方案输出格式

- bullet point，默认简短；复杂改动允许展开，但每个候选项仍需一句话取舍
- 不写完整代码，只写必要的关键伪代码
- 必须包含：
  1. **根因 / 目标**（一句话）
  2. **候选方案及取舍**（bug 可一个方案，设计必须两个以上）
  3. **影响面 / 风险**（动到哪些模块、兼容性、数据迁移、回滚方式）
  4. **验证方式**（怎么证明修好了/做对了：测试、命令、人工检查点）
  5. **需要用户拍板的决策点**（明确标出，不要让用户猜哪里需要他）

## 自我追问（代替用户问"为什么"）

方案末尾主动追加，不等用户问：
- **我还想追问的为什么**：对方案逐层问"为什么这样做"，直到问不出新的——把还有真实疑问的列出来
- **最不确定的 3 个点**
- **可能出错的边界情况**

## 红线

- 不接受"先跑起来再说"式的方案——方案里出现就自问自答地挑战它
- 方案里每个改动都要能回答"为什么是这个而不是更简单的做法"
- 闸门没有被绕过的方式：用户说"直接改吧"也算确认，但必须用户明说
