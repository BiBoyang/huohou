# Code Review（通用评审纪律）

**本 skill 是判断指南，不是勾选清单。** 不要机械逐条打勾；每条检查都要落到"这个 diff 的具体证据"上。

## 开始之前：重建上下文

1. 确认评审对象的真实范围：PR 的 live base 和 head、diff 全文，以及理解设计所需的**周边代码**——只读 diff 无法做语义评审。
2. 先读目标仓库自己的规范来源：`AGENTS.md`、贡献指南、docs/、ADR/设计文档。仓库规则优先于本 skill 的通用建议；与仓库既有设计文档分歧时，把它当设计讨论提出，而不是自动否决。
3. 只读 diff 无法判断的东西（意图、历史决策、跨模块约定），去查对应文档和提交记录，不要猜。

## 优先级

按此顺序分配注意力，前面的没查完别纠结后面的：

1. **正确性**：实现是否匹配声称的意图；边界条件；错误路径。
2. **生命周期与并发**：竞态、取消、资源清理、所有权。
3. **安全**：deny 路径是否真的被执行；注入面；权限边界。
4. **破坏既有行为**：公开契约、默认值、输出格式的变化。
5. 风格与命名——最后，且能用工具强制的不要占用评审评论。

一个有证据支撑的 blocker，胜过一长串 nit 清单。短评审 + 硬核问题 > 面面俱到的流水账。

## 硬性卡口（违反即 blocker）

- **文档与代码同步**：配置项、默认值、错误信息、公开行为的变更，必须在同一 diff 里更新对应文档和注释。注释只写非显而易见的契约——复述实现、测试流水账、评审历史的注释应要求删除。
- **资源/注册有对应清理**：新增的监听器、订阅、注册项、进程、句柄，必须有对应的移除/释放路径，且有测试覆盖。
- **测试证据存在**：作者确实跑过相关检查；CI 覆盖该覆盖的矩阵。覆盖率数字本身不是场景正确的证据。

## 语义检查（需要人工判断的部分）

- **接口双侧追踪**：每个改动的接口，把调用方和被调方都走一遍。确认错误语义、取消行为、所有权归属在两侧一致。
- **并发与 teardown**：异步初始化、回调、子进程、销毁路径——检查发布前的竞态、await 期间的取消、错误的独立上报、回调不外泄、reentry 前的所有权、detach 清理是否完整。
- **消费方匹配**：追踪每个公开接口的所有真实调用方。两种反向都要抓：某个消费方的专用逻辑泄露进通用接口；以及——通用服务上新增的公开方法只有一个内部调用方（不必要的 API 扩张，应改为构造时注入的私有能力）。
- **范围与必要性**：把每个新抽象、状态机、配置项、兼容路径映射到它当前的契约和真实消费方。挑战与本次目标无关的特性和投机性的通用化。
- **默认值与公开选择**：每个默认值、公开操作集、格式，问一句"有什么证据/先例支撑？"没有证据的要求作者做出显式选择或显式推迟。
- **借用还是拥有**：每个被保留的值，判断它是借用还是拥有；追溯每个缓存、回显、重放、查询视图是否追到权威数据源，而不是二手状态。
- **边界覆盖最终产出**：找到完整产出（含包装层和元数据）的尺寸负责人；用极小值、恰好等于上限、超大单块、多字节文本去戳边界。
- **真实入口路径**：测试要走真实的发货入口（loader/bin/worker/子进程），而不是手工挂载的替身——替身测不出入口导出错误。
- **测试强度**：断言是否真的能在目标回归发生时失败？验证的是外部可观测状态（事件、日志、副作用、资源释放），还是只是在复述实现细节？
- **可见输出变更**：快照、日志、用户可见文本的变化按行为变更评审，不当格式噪音放过。

## 报告纪律

- 每条发现写清四要素：**缺陷、位置、影响、证据**。
- 局部缺陷挂在最紧凑的相关 diff 行内；跨架构、范围、整体性的问题写顶层评论。
- blocker 与建议明确分开；已被绿色卡口强制保证的问题不再重复提。
- 回复走既有讨论串，不开新战场。

## 被评审时（你作为作者）

- 逐条**核实**评审意见再响应：对的修，错的基于技术理由反驳。
- 不表演性认同——"你说得对"然后不改，和为了显得合作而接受错误意见，都是坏结果。
- 与仓库设计文档冲突的意见，展开成设计讨论。
