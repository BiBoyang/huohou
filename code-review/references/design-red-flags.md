# Red Flags 完整评审清单

Ousterhout 在全书总结中给出的危险信号。评审代码/设计时逐条对照。每条给出：识别标准 → 为什么有害 → 怎么修。

> 用法：对目标代码逐条检查；命中的条目，在评论中写清"信号 → 复杂度症状（变更放大/认知负荷/未知的未知）→ 建议修法"。

## 模块结构类

### 1. 浅模块（Shallow Module）
- **识别**：模块/类/方法的接口复杂度不亚于其实现；调用它比自己写内联代码还费劲。
- **危害**：接口引入新依赖却没有换来实现简化——纯增复杂度。
- **修法**：合并进调用方或相邻模块；或者增强实现让接口显得更便宜（变深）。

### 2. 信息泄露（Information Leakage）
- **识别**：同一设计决策/知识（格式、协议、约定、魔数）出现在多个模块中；改它要同步改多处。
- **危害**：变更放大 + 未知的未知（漏改一处就炸）。
- **修法**：把知识收拢到唯一模块，其他处通过接口访问。

### 3. 时间顺序分解（Temporal Decomposition）
- **识别**：模块按执行先后切分（"读取模块""解析模块""校验模块"），导致多个模块都必须知道同一份信息（如文件格式）。
- **修法**：改按"信息拥有权"切分——让一个模块完整拥有一份知识。

### 4. 过度暴露（Overexposure）
- **识别**：API 强迫调用者了解/配置极少用到的功能才能使用常用功能。
- **修法**：常用路径给默认值/自动推断；罕见功能下沉到独立接口。

### 5. 透传方法（Pass-Through Method）
- **识别**：方法只把参数转交给另一个签名相似的方法，自身不产生新抽象。
- **修法**：责任上移/下移合并掉中间层；若中间层是 dispatcher 且有路由价值则保留。

### 6. 重复（Repetition）
- **识别**：同一代码段反复出现；改 bug 要改 N 处。
- **修法**：提取公共实现。注意区分"代码看起来相同"与"知识相同"——前者有时可接受，后者必须合并。

### 7. 通用-专用混杂（Special-General Mixture）
- **识别**：通用机制（框架、工具类、底层接口）里掺入某个特定调用方的专用逻辑。
- **修法**：把专用部分上推到调用方或独立模块，让通用机制保持干净和深。

### 8. 连体方法（Conjoined Methods）
- **识别**：两个方法必须按特定顺序/配合使用才正确；不看另一个就无法理解这一个。
- **修法**：合并成一个方法，或重新划分职责。

## 注释类

### 9. 注释复述代码（Comment Repeats Code）
- **识别**：注释里的全部信息都能从紧邻代码直接读出（`i++; // increment i`）。
- **修法**：删掉，或改写成代码看不出来的信息（为什么、约束、单位）。

### 10. 接口注释污染实现（Implementation Documentation Contaminates Interface）
- **识别**：类/方法的接口注释描述内部算法、数据结构等实现细节。
- **危害**：破坏信息隐藏——使用者被迫关心内部，接口比实际需要更复杂。
- **修法**：接口注释只写契约（做什么、输入输出语义、副作用）；实现细节移到实现注释。

### 11. 含糊的命名（Vague Name）
- **识别**：名字太泛不携带信息（`data`、`result`、`handle`、`doIt`），或让读者会猜错。
- **修法**：换成精确名字；若找不到精确名字，见下一条。

### 12. 难以命名 / 难以描述（Hard to Pick Name / Hard to Describe）
- **识别**：给一个实体起不出精确直观的名字；或描述它需要又长又绕的文字。
- **危害**：这几乎总是**设计本身**的信号——职责不清、抽象边界错了。
- **修法**：不要硬起名字，先重设计；设计对了名字自然出现。

## 代码可读性类

### 13. 不显而易见的代码（Nonobvious Code）
- **识别**：读者无法第一遍正确理解行为或含义——控制流被事件/回调打散、类型掩盖了内容（`Map<String, Object>`）、行为违反命名预期。
- **修法**：优先改结构让代码直白；无法改结构时用注释点破关键决策；让同事读一遍验证。

## 评审输出模板

发现问题的评论格式建议：

```
[Red Flag] <信号名>
位置：<文件:行>
症状：<变更放大 / 认知负荷 / 未知的未知>
根因：<依赖 / 模糊，具体说明>
建议：<按上面"修法"给具体改法>
```

## 最后的平衡

这些信号是"警示"不是"禁令"。命中一条先停下来想："这里有没有更简单的做法？"——如果有且成本相当，就该改；如果改掉它反而引入更大的复杂度（过度设计），保持现状并在注释里说明理由。Ousterhout 的立场永远是：**复杂度是唯一的标尺**。
