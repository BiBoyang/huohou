# Code Review（通用评审纪律）

> 注意：与 Claude Code 官方插件市场的 `/code-review` 插件（PR 评论自动化工具）是两个东西——那个管"把评论发回 GitHub PR"，本 skill 管"怎么判断和报告"。两者可配合：先按本 skill 的纪律做语义评审，需要发到 PR 时再调官方插件。

**本 skill 是判断指南，不是勾选清单。** 不要机械逐条打勾；每条检查都要落到"这个 diff 的具体证据"上。

## 开始之前：重建上下文

1. 确认评审对象的真实范围：PR 的 live base 和 head、diff 全文，以及理解设计所需的**周边代码**——只读 diff 无法做语义评审。
2. 先读目标仓库自己的规范来源：`AGENTS.md`、贡献指南、docs/、ADR/设计文档。仓库规则优先于本 skill 的通用建议；与仓库既有设计文档分歧时，把它当设计讨论提出，而不是自动否决。
3. 只读 diff 无法判断的东西（意图、历史决策、跨模块约定），去查对应文档和提交记录，不要猜。
4. 提问纪律（双向）：仓库、文档、git 记录能查到的不问人（不懒）；缺判断意图/约束所需的关键材料时，先问"是否还有相关资料"——外部设计文档、wiki、其他仓库，补材料优先于逐条问答（不硬猜）。一次最多 3 个关键问题；普通不确定性标注后继续，不中断评审。

## 先审路线，再审代码（触发式）

技术路线本身是取舍，没有完美方案。**已深思熟虑定下的路线，不要每次评审重新挑战。** 满足任一跳过条件，一句话带过路线判断，直接进入实现审查：

- 用户显式声明路线已定（"只审实现"/"路线不用审"）；
- 仓库 ADR/设计文档已记录该路线决策，且本次改动在既定路线内；
- 纯局部修复的小 diff，且无路线层危险信号。

触发条件（且未被跳过）：用户要求方案/整体评审；或实现审查中发现**路线层危险信号**——同类问题反复打补丁、权限/状态/安全问题源自架构本身、简单问题被做复杂。

触发时：

1. 先还原"这次改动要解决什么问题"（依据 README/docs/提交记录，注明出处），不默认现有方案正确。
2. 判断问题能否局部修复；若存在有意义的替代方案能从根源消除这一类问题，按需求覆盖、安全风险、实现复杂度、维护成本、影响范围、迁移/回滚难度比较取舍。
3. 输出路线结论：**保留 / 调整 / 更换 / 信息不足**。结论未定之前，不出代码级补丁清单。
4. 不强行编造替代方案——当前方案合理，直接说值得保留并给理由。不被沉没成本绑架：写了很多代码不代表路线该继续。

边界：已定路线不是免审金牌。实现审查中冒出**新证据**直接 contradict 路线时，按"设计讨论"提一次，不自动否决，不反复纠缠。

若偏差根因不在代码也不在方案，而在需求里没写明的地带（脑补偏差）：结论是**回需求层对齐**——补 spec 再回来，不在代码层打补丁。

## 优先级

按此顺序分配注意力，前面的没查完别纠结后面的：

1. **正确性**：实现是否匹配声称的意图；边界条件；错误路径。
2. **生命周期与并发**：竞态、取消、资源清理、所有权。
3. **安全**：deny 路径是否真的被执行；注入面；权限边界。
4. **破坏既有行为**：公开契约、默认值、输出格式的变化。
5. 风格与命名——最后，且能用工具强制的不要占用评审评论。

一个有证据支撑的 blocker，胜过一长串 nit 清单。短评审 + 硬核问题 > 面面俱到的流水账。

## 硬性卡口（违反即 blocker）

- **文档与代码同步**：配置项、默认值、错误信息、公开行为的变更，必须在同一 diff 里更新对应文档和注释。注释只写非显而易见的契约——复述实现、测试流水账、评审历史的注释应要求删除。
- **资源/注册有对应清理**：新增的监听器、订阅、注册项、进程、句柄，必须有对应的移除/释放路径，且有测试覆盖。
- **测试证据存在**：作者确实跑过相关检查；CI 覆盖该覆盖的矩阵。覆盖率数字本身不是场景正确的证据。
- **验证声明有据**：评审中每个"已验证/测试通过/已修复"的声明，必须指向本轮真实跑过的命令和输出；没跑就明说"基于读代码"。假绿不算绿：被跳过的用例、空输出让断言通过的、声称修复但从没看过实际结果的，都不算验证。

## 语义检查（需要人工判断的部分）

- **接口双侧追踪**：每个改动的接口，把调用方和被调方都走一遍。确认错误语义、取消行为、所有权归属在两侧一致。
- **并发与 teardown**：异步初始化、回调、子进程、销毁路径——检查发布前的竞态、await 期间的取消、错误的独立上报、回调不外泄、reentry 前的所有权、detach 清理是否完整。
- **消费方匹配**：追踪每个公开接口的所有真实调用方。两种反向都要抓：某个消费方的专用逻辑泄露进通用接口；以及——通用服务上新增的公开方法只有一个内部调用方（不必要的 API 扩张，应改为构造时注入的私有能力）。
- **范围与必要性**：把每个新抽象、状态机、配置项、兼容路径映射到它当前的契约和真实消费方。挑战与本次目标无关的特性和投机性的通用化。每个改动文件、每个新公开面都要能一句话追溯回本次声明的目标；追溯不了的标为 drift，要求作者解释或移出。
- **同类实例扫描**：diff 修的是一类 bug 的单个实例（缺校验、选错选择器、off-by-one、漏加锁）时，提取模式签名全仓 grep（排除生成目录），确认兄弟实例已一并处理；未处理的同风险实例按 blocker 提，低风险的按建议提。
- **默认值与公开选择**：每个默认值、公开操作集、格式，问一句"有什么证据/先例支撑？"没有证据的要求作者做出显式选择或显式推迟。
- **借用还是拥有**：每个被保留的值，判断它是借用还是拥有；追溯每个缓存、回显、重放、查询视图是否追到权威数据源，而不是二手状态。
- **边界覆盖最终产出**：找到完整产出（含包装层和元数据）的尺寸负责人；用极小值、恰好等于上限、超大单块、多字节文本去戳边界。
- **真实入口路径**：测试要走真实的发货入口（loader/bin/worker/子进程），而不是手工挂载的替身——替身测不出入口导出错误。
- **测试强度**：断言是否真的能在目标回归发生时失败？验证的是外部可观测状态（事件、日志、副作用、资源释放），还是只是在复述实现细节？
- **可见输出变更**：快照、日志、用户可见文本的变化按行为变更评审，不当格式噪音放过。

## 报告纪律

- 每条发现写清四要素：**缺陷、位置、影响、证据**；再补三个标注：**严重度**（blocker/高/中/低）、**置信度**（已确认缺陷 / 合理推断 / 待验证猜测——无证据时，理论可能性不写成已存在的 bug）、**根因还是症状**。
- **高严重度过证据门**：blocker/高 的发现必须给齐三样——精确到行的位置、触发的具体输入/状态/时序、为什么现有防护（校验、类型系统、上游 catch、框架默认值）没拦住。给不齐就降级或丢弃；"某条件下可能会炸"不算高。
- 同一根因的多个发现合并成一条，优先给根因修法，不拆成 N 条凑数量。
- 局部缺陷挂在最紧凑的相关 diff 行内；跨架构、范围、整体性的问题写顶层评论。
- blocker 与建议明确分开；已被绿色卡口强制保证的问题不再重复提。
- 结尾给**最优先处理的三件事**和**可暂时接受的剩余风险**，不平铺所有发现。
- 回复走既有讨论串，不开新战场。
- **一轮查透，不挤牙膏**：第一轮就沿调用方、数据流、受影响范围查到底，不只查局部补丁。复审只跟进上轮遗留和本轮新引入；复审冒出"早就存在的新问题"，说明第一轮失职，不是认真。评审中应用过任何 fix 后，旧结论作废：重读当前 HEAD、工作区状态和完整 diff，再下复审结论。
- **无货直说**：没有新的重要发现时直接说没有，不凑数；判断已进入收益递减，明确建议停止。

## 被评审时（你作为作者）

- 逐条**核实**评审意见再响应：对的修，错的基于技术理由反驳。
- 不表演性认同——"你说得对"然后不改，和为了显得合作而接受错误意见，都是坏结果。
- 与仓库设计文档冲突的意见，展开成设计讨论。
