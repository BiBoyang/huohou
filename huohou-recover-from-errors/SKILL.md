# recover-from-errors（报错恢复，防越修越偏）

## 核心问题

反复报错时最大的风险不是错误本身，而是**漂移**：猜参数、换路径、换工具，每一次"试试看"都往上下文里塞噪音，几轮之后已经离原始目标十万八千里，还在修一个根本不是问题的问题。

## 先分类，再动手

第一次报错时先判断失败类型，类型决定下一步：

- **瞬时/环境类**（网络超时、TLS/SSL 握手失败、rate limit、临时锁、资源暂时不可用）：允许**原命令原参数**有界重试——带间隔，最多 3 次。重试前可用只读探针确认通道健康（如 `gh api user`、一次小读取）。这不违反"禁止盲目重试"：探针证据就是"这次为什么应该不一样"的答案。
- **确定类**（参数错、路径错、逻辑错、断言失败）：同参数重试零价值，直接走下面的恢复流程。
- **分不清**：先留证，再用只读操作缩小失败层面，不要带着模糊判断直接改。

重试或修复之前**先留证**：保存完整报错原文、退出码、日志路径。上下文滚动后诊断依据就没了，硬停止报告的"卡点描述"也靠它。

## 恢复流程

确定类失败连续出现 **2 次**（或同一点位第 2 次失败）时，停止重试，执行（瞬时类的有界重试不计入计数；有界重试耗尽仍失败，转为确定类处理）：

1. **回到锚点**：重新读一遍原始目标——用户的要求、huohou-plan-first 的方案、或任务计划。问自己：**"我刚才试图做的这个动作，是方案里明确要求的吗？"**

2. **分两种情况**：
   - **动作在方案内，是执行细节错了**（路径错、参数错、前置缺失）→ 分析具体原因，修这个具体问题，再继续
   - **动作不在方案内，或方案里根本没有这一步** → **立即停止这条线**。你已经偏航了。回到方案，从最近的正确节点重新走；必要时向用户说明"我刚才偏离了方案，现在回到正轨"

3. **修因不修表**：报错信息要读到根因层。"文件不存在"要问为什么不存在（目录错了？前置步骤没跑？），而不是换个文件继续。

4. **回原点位验证**：修完用**原始失败的那条命令**（不是变体）确认通过，再走下一步——防止修复本身引入新偏差还自以为过了。

## 跑完 ≠ 成功

命令或后台任务结束后，必须核对真实结果（退出码、关键输出、目标状态）再推进。"任务已完成"不代表成功——输出里可能是 `fatal`，push 可能根本没上去。

## 硬停止条件（满足任一即停，向用户报告）

- 同一点位修复尝试 **3 次**仍失败
- 要继续需要改动方案/任务范围之外的东西
- 失败原因超出当前任务的知识范围（环境损坏、权限、依赖本身有问题）

停止时输出三样东西：**当前状态、已改动的内容、卡点描述**——不硬试、不擅自回滚、不假装修好了。

## 红线

- 禁止"换个参数试试"式的盲目重试——每次重试必须先说出"这次为什么应该不一样"（瞬时/环境类的答案是探针证据，见「先分类，再动手」）
- 禁止为消除报错而扩大改动范围（报错在原函数，不要去重构调用方）
- 禁止静默绕过：注释掉报错代码、`|| true`、吞异常——除非用户明确批准
